## The "vibes-based evaluation" trap

Every AI engineer falls into this trap early: you ask your RAG system five questions, the answers look reasonable, and you declare it working. Then your manager asks a different question and gets a hallucinated answer. The problem is that you tested anecdotally, not systematically.

Production AI systems need two types of evaluation: **retrieval evaluation** (did you find the right documents?) and **generation evaluation** (did the LLM produce a correct, grounded answer?).

## Retrieval metrics

These measure whether your vector search returns the right documents.

### Precision@k

Of the k documents you retrieved, how many were actually relevant?

```
precision@5 = (relevant docs in top 5) / 5
```

If you retrieve 5 documents and 3 are relevant, precision@5 = 0.6.

### Recall@k

Of all the relevant documents in your corpus, how many did you retrieve in the top k?

```
recall@5 = (relevant docs in top 5) / (total relevant docs)
```

If there are 4 relevant documents total and you retrieved 3 of them, recall@5 = 0.75.

### Mean Reciprocal Rank (MRR)

Where does the *first* relevant document appear in the ranked list?

```
MRR = 1 / rank_of_first_relevant_result
```

If the first relevant document is at position 1, MRR = 1.0. If it's at position 3, MRR = 0.33. Averaged across all queries, this tells you how often you're putting the best result at the top.

## Generation metrics

These measure whether the LLM's answer is correct and grounded.

### Faithfulness

Does the answer only contain information that is supported by the retrieved context? An answer is unfaithful if it adds facts not present in the context (hallucination).

To measure faithfulness, you can:
1. Break the answer into individual claims
2. Check whether each claim is supported by the retrieved passages
3. Faithfulness = (supported claims) / (total claims)

### Answer relevancy

Does the answer actually address the user's question? An answer can be faithful (everything it says is in the context) but irrelevant (it talks about the wrong topic).

### Practical measurement

You can measure these automatically using an LLM-as-judge pattern:

```python
def evaluate_faithfulness(answer: str, context: str) -> float:
    """Use an LLM to check if every claim in the answer is supported by context."""
    prompt = f"""Given this context and answer, list every factual claim in the answer.
For each claim, say whether it is SUPPORTED or NOT SUPPORTED by the context.

Context: {context}
Answer: {answer}

Output a JSON list of {{"claim": "...", "supported": true/false}}"""
    
    result = call_llm(prompt)
    claims = json.loads(result)
    supported = sum(1 for c in claims if c["supported"])
    return supported / len(claims) if claims else 0.0
```

## Building an evaluation harness

A minimal evaluation harness has three components:

### 1. A test dataset

Create a JSON file with at least 20 question-answer-context triples:

```json
[
  {
    "question": "What is the refund policy for annual plans?",
    "expected_answer": "Annual plans can be refunded within 30 days.",
    "relevant_doc_ids": ["doc_047", "doc_048"]
  }
]
```

### 2. A runner that computes metrics

```python
def evaluate(test_cases, retriever, generator):
    results = []
    for case in test_cases:
        retrieved = retriever.search(case["question"], k=5)
        retrieved_ids = [r.doc_id for r in retrieved]
        answer = generator.generate(case["question"], retrieved)
        
        p_at_5 = precision_at_k(retrieved_ids, case["relevant_doc_ids"], k=5)
        r_at_5 = recall_at_k(retrieved_ids, case["relevant_doc_ids"], k=5)
        faith = evaluate_faithfulness(answer, retrieved)
        
        results.append({"p@5": p_at_5, "r@5": r_at_5, "faithfulness": faith})
    return aggregate(results)
```

### 3. A baseline to compare against

Always run your evaluation twice: once with the current system (baseline) and once with the change you're testing. Report the delta. A 2% improvement in precision@5 might not justify switching to a more expensive embedding model.

## How many test cases do you need?

- **Minimum viable**: 20 hand-labeled cases to catch obvious regressions
- **Solid**: 50-100 cases covering different query types and edge cases
- **Production-grade**: 200+ cases, refreshed quarterly, with inter-annotator agreement checks

The investment in building a good test set pays for itself every time you make a change. Without it, every change is a gamble.

<BookNote chapter="3">

Huyen argues that evaluation is the biggest obstacle to shipping AI products, and that it gets
harder as models get better. A smarter model writes answers that look right to a casual reader,
so spotting the wrong ones takes more effort. Open-ended tasks also lack a single correct output,
which rules out the simple accuracy checks you learned in ML courses.

The chapter sorts the options into a few families. Exact methods work when there is something
concrete to compare against: does the generated code pass its tests, does the extracted field
match the label, how close is the output to a reference answer. When nothing concrete exists,
teams use a second model as a judge, or people review samples by hand.

The useful takeaway for an app builder is to match the method to the task. If you can turn a
requirement into something a program can check, do that first, because it is cheap, fast and
repeatable. Save judge models and human review for qualities a program cannot measure, and keep
some human review even when automated scores look healthy.

Further reading: Chip Huyen, AI Engineering (O'Reilly, 2025), chapter 3

</BookNote>

```python
from dataclasses import dataclass

@dataclass
class EvalCase:
    question: str
    relevant_doc_ids: list[str]

def precision_at_k(retrieved_ids: list[str], relevant_ids: list[str], k: int) -> float:
    top_k = retrieved_ids[:k]
    relevant_in_top_k = len(set(top_k) & set(relevant_ids))
    return relevant_in_top_k / k

def recall_at_k(retrieved_ids: list[str], relevant_ids: list[str], k: int) -> float:
    top_k = retrieved_ids[:k]
    relevant_in_top_k = len(set(top_k) & set(relevant_ids))
    return relevant_in_top_k / len(relevant_ids) if relevant_ids else 0.0

def mrr(retrieved_ids: list[str], relevant_ids: list[str]) -> float:
    for rank, doc_id in enumerate(retrieved_ids, start=1):
        if doc_id in relevant_ids:
            return 1.0 / rank
    return 0.0

# Example usage
retrieved = ["doc_3", "doc_1", "doc_7", "doc_2", "doc_9"]
relevant = ["doc_1", "doc_2"]

print(f"P@5: {precision_at_k(retrieved, relevant, 5)}")   # 0.4
print(f"R@5: {recall_at_k(retrieved, relevant, 5)}")       # 1.0
print(f"MRR: {mrr(retrieved, relevant)}")                   # 0.5
```

<CommonMistakes>
- **Evaluating with too few test cases** — 5 queries tells you almost nothing; aim for 20+ minimum
- **Only measuring generation quality, ignoring retrieval** — if retrieval is broken, no amount of prompt engineering fixes the answers
- **Using the same LLM to generate and judge** — the model will be biased toward its own outputs; use a stronger model as judge or use human labels
- **Not establishing a baseline before making changes** — without a before/after comparison, you can't know if your change helped
</CommonMistakes>
