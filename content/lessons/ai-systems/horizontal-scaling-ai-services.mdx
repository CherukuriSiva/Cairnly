<WhyThisMatters>
One inference process handles a handful of concurrent requests before latency spikes. Real traffic needs many. Knowing how to scale horizontally — and which signals to autoscale on — is what keeps p95 latency flat under load and is a standard production-engineering interview line.
</WhyThisMatters>

<Body>
## Vertical first, then horizontal

- **Vertical** — a bigger box / GPU. Simple, but capped and a single point of failure.
- **Horizontal** — many identical worker replicas behind a load balancer. Near-unlimited and fault-tolerant. This is how you scale serving.

## Make workers stateless

Horizontal scaling only works if any worker can serve any request. Keep per-request state out of the worker: session/memory in Redis or a DB, the model loaded read-only at startup. No sticky local state means the load balancer can route freely and replicas can come and go.

## Autoscale on the right signal

CPU% is a poor proxy for an inference service. Better signals:

- **Request queue depth / concurrency** — the most direct measure of "we need more workers."
- **p95 latency** — scale out before users feel it.
- **GPU utilization** — for GPU-bound inference.

## The AI-specific traps

- **Model load time** — a new replica isn't useful until the model loads; warm pools or readiness probes prevent routing to cold workers.
- **GPU contention** — too many workers per GPU thrash; pin worker-per-GPU ratios.
- **Thundering herd on cold start** — scale ahead of demand, not reactively at the spike.
</Body>

<Code>
```python
# Multiple Uvicorn workers behind a load balancer; each loads the model once.
# uvicorn serve:app --workers 4 --host 0.0.0.0 --port 8000

# Kubernetes HPA autoscaling on a custom concurrency metric (sketch):
# apiVersion: autoscaling/v2
# kind: HorizontalPodAutoscaler
# spec:
#   minReplicas: 2
#   maxReplicas: 20
#   metrics:
#     - type: Pods
#       pods:
#         metric: { name: inflight_requests }   # queue depth, not CPU
#         target: { type: AverageValue, averageValue: "8" }

# Readiness probe so traffic only routes to workers whose model finished loading:
@app.get("/ready")
async def ready():
    return {"ready": model is not None}, (200 if model is not None else 503)
```
</Code>

<CommonMistakes>
- **Autoscaling on CPU%** — a poor proxy; use concurrency or p95 latency
- **Stateful workers** — sticky local sessions break free routing
- **Ignoring model load time** — traffic hits cold workers and times out
- **Over-packing GPUs** — too many workers per GPU thrashes throughput
- **Reactive-only scaling** — scale ahead of predictable spikes
</CommonMistakes>
