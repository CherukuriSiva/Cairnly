<WhyThisMatters>
The API contract is the agreement between your AI backend and everyone who calls it. Get it right and frontends, partners, and admins integrate cleanly; get it wrong and every change is a breaking change. "Sketch the API for an enterprise RAG product" is a frequent system-design prompt, and a crisp set of boundaries is the senior answer.
</WhyThisMatters>

<Body>
## Three boundaries

A RAG product splits cleanly into three services, each a versioned prefix (`/api/v1/...`):

- **Ingestion** — onboard documents (admin/system auth). Async, so it returns `202` + `job_id` with a status endpoint.
- **Retrieval & generation** — the user-facing chat. Auth is a **user JWT carrying RBAC claims**; responses stream via SSE.
- **Telemetry & analytics** — admin-only health, drift, and security-event endpoints.

Separating these keeps auth, scaling, and rate limits independent per concern.

## Match response style to the work

- **Ingestion** → `202 Accepted` (long-running) — never block.
- **Chat** → **SSE stream**, where the final chunk includes a `cited_sources` array for lineage.
- **Analytics** → plain `200` JSON.

A one-size-fits-all JSON response forces slow blocking on ingestion and kills streaming UX on chat.

## Auth and RBAC ride in the contract

The chat request carries a user JWT whose claims include the user's roles. Those claims flow straight into the retrieval pre-filter (the RBAC-for-RAG lesson) so a user only ever retrieves what they're allowed to see. Ingestion uses a stronger admin/system token. Auth isn't a separate system — it's part of the request shape.

## Return lineage, not just an answer

For a RAG product, the answer without sources is half a response. The chat contract returns `cited_sources` so the user can verify the answer and you can audit it. Make citations a first-class field, not an afterthought.
</Body>

<Code>
```text
POST /api/v1/ingest/document        (admin/system token)
  payload: file blob, document_metadata, allowed_roles[]
  → 202 Accepted  { "job_id": "job-1234" }
GET  /api/v1/ingest/status/{job_id} → { "status": "Embedding" }

POST /api/v1/chat/completions       (user JWT with RBAC claims)
  payload: { "messages": [...], "session_id": "uuid", "stream": true }
  → text/event-stream; final chunk: { "cited_sources": ["doc-104A", ...] }

GET  /api/v1/analytics/drift         (admin token)
  → 200 { "average_similarity_score": 0.82, "top_missing_topics": [...] }
GET  /api/v1/analytics/security_events  → 200 paginated injection attempts
```

<CommonMistakes>
- **One response style for everything** — blocks ingestion, kills chat streaming
- **No API versioning prefix** — every change risks breaking clients
- **Auth as an afterthought** — RBAC claims must be part of the contract and reach retrieval
- **Returning answers without citations** — a RAG response needs lineage
- **Mixing admin and user endpoints under one auth** — separate the boundaries
</CommonMistakes>
