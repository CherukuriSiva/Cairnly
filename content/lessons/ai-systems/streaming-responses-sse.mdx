<WhyThisMatters>
A 4-second wait for a full answer feels broken; the same 4 seconds with words appearing immediately feels fast. Streaming is the single biggest *perceived* latency win in LLM UX, which is why every serious chat product does it. Knowing SSE vs WebSockets and the guardrail trade-off is a common production-engineering question.
</WhyThisMatters>

<Body>
## Time-to-first-token beats total time

Users judge responsiveness by **time to first token**, not total generation time. Streaming sends each token as it's produced, so the answer starts appearing in ~200ms even if it takes 4s to finish. Same total time, completely different feel.

## SSE vs WebSockets

- **SSE (Server-Sent Events)** — one-way, server→client, over plain HTTP. Simple, auto-reconnects, perfect for "stream the model's tokens to the browser." This is the default for LLM streaming.
- **WebSockets** — full duplex, bidirectional. Use when the client also needs to send mid-stream (interrupt, collaborative editing, live tools). More moving parts.

For a chatbot that streams an answer, **SSE is usually the right, simpler choice.**

## The guardrail trade-off

Here's the catch: once you stream a token, it's on the user's screen. You can no longer run an *output* guardrail over the *complete* answer before showing it. Options:

- Run **input** guardrails before streaming starts (you still can).
- **Buffer-and-scan** small windows, or stop the stream if a check trips.
- For high-stakes domains, **don't stream** — generate fully, verify, then return.

Streaming is a UX win you pay for in output-moderation flexibility.
</Body>

<Code>
```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

async def token_stream(query: str):
    # input guardrails run BEFORE the first token leaves
    if not is_safe_prompt(query):
        yield "data: [blocked]\n\n"
        return
    async for token in llm.stream(query):     # provider yields tokens
        yield f"data: {token}\n\n"             # SSE frame
    yield "data: [DONE]\n\n"

@app.get("/chat")
async def chat(q: str):
    return StreamingResponse(token_stream(q), media_type="text/event-stream")
```
</Code>

<CommonMistakes>
- **Reaching for WebSockets** when one-way SSE would do
- **Assuming you can still moderate the full output** — once streamed, it's shown
- **No `[DONE]` sentinel** — clients can't tell when the stream ended
- **Streaming high-stakes answers** that need full-output verification
- **Forgetting input guardrails** — you can still run those before streaming
</CommonMistakes>
