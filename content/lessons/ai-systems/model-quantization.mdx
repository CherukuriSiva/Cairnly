<Body>
## What quantization is

Models store weights as numbers. Quantization stores them with **fewer bits** — FP32 (32-bit) → INT8 (8-bit) is 4× smaller. Smaller weights mean less memory bandwidth, which is what inference is usually bottlenecked on, so it's also faster.

## The precision ladder

- **FP32** — full precision; the training default; biggest and slowest.
- **FP16 / BF16** — half precision; ~2× smaller, widely used for serving with negligible accuracy loss.
- **INT8** — 8-bit integers; ~4× smaller, fastest; needs a *calibration* step and risks more accuracy loss.

Lower precision = cheaper and faster, but accuracy can degrade — so you must measure.

## Measure the trade-off, don't assume it

Quantization is only a win if quality holds. Run your **eval harness** on the quantized model and compare to the FP32 baseline. If F1 drops within your tolerance, ship it; if it falls off a cliff, step back up the ladder (e.g. INT8 → FP16).

## Micro-batching for throughput

Even quantized, serving one request at a time wastes the accelerator. **Dynamic micro-batching** collects requests that arrive within a few milliseconds and runs them as one batch — big throughput gains for a tiny added latency. Tune the batch window against your latency budget.
</Body>

<BookNote chapter="9">

Chapter 9 is about making inference faster and cheaper, and quantization is one of the most
common tools. The idea is to store numbers with fewer bits. Model weights trained in 32 or 16 bit
formats can often be kept in 8 or even 4 bits with only a small drop in quality.

Fewer bits help in two ways. The model takes less memory, so it fits on smaller or fewer GPUs.
And because generating text is often limited by how fast weights move from memory rather than
by raw compute, smaller weights can also mean faster responses.

Huyen separates doing this after training from building it into training. Post-training
quantization is the easy path: take a finished model and convert it. Quantization-aware training
simulates low precision while training so the model learns to cope, which helps keep quality at
very low bit widths.

The trade-off is quality, and it varies by task and model. Some skills, such as maths or long
reasoning, can degrade more than casual chat. So treat a quantized model as a new model and run
your own evaluation set before you swap it in.

Further reading: Chip Huyen, AI Engineering (O'Reilly, 2025), chapter 9

</BookNote>

```python
# Gate the swap on an eval comparison, not vibes:
def accept_quantized(fp32_model, int8_model, harness, tolerance: float = 0.01) -> bool:
    base = harness.run_factuality_model(fp32_model)["mean_f1"]
    quant = harness.run_factuality_model(int8_model)["mean_f1"]
    print(f"FP32 F1={base:.3f}  INT8 F1={quant:.3f}  Δ={base - quant:.3f}")
    return (base - quant) <= tolerance   # ship only if accuracy loss is within budget
```

<CommonMistakes>
- **Quantizing without measuring accuracy** — you may ship a quietly worse model
- **Jumping straight to INT8** — try FP16/BF16 first; often free quality
- **Ignoring calibration for static INT8** — uncalibrated INT8 can tank accuracy
- **Micro-batch window too large** — throughput up, but latency budget blown
- **Assuming smaller is always faster** — gains depend on the hardware and bottleneck
</CommonMistakes>
