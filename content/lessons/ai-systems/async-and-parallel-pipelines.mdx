<WhyThisMatters>
A RAG request is a chain of network calls — embed, retrieve, guardrail-check, generate — and done sequentially the latencies add up. Many of those stages are *independent* and can overlap. Restructuring the pipeline to run independent work concurrently is one of the cleanest latency wins available, and async fluency is expected of any production AI engineer.
</WhyThisMatters>

<Body>
## Why async, specifically

LLM/RAG work is **I/O-bound** — most of the wall-clock time is spent *waiting* on a network response (the embedding API, the vector DB, the LLM). While one call waits, the CPU is idle. Async lets you fire off independent waits at once and collect them together, so total latency approaches the *slowest* call instead of the *sum*.

## Find the independent stages

In a typical request:

- Embedding the query and running the **input guardrail** (injection/PII check) don't depend on each other → run them together.
- After retrieval, an output-side step and a logging/telemetry write can overlap.
- A multi-source agent can query the internal KB and the web **in parallel**.

Anything with no data dependency is a parallelization candidate.

## Run them with `asyncio.gather`

`asyncio.gather` launches coroutines concurrently and waits for all. The "guardrail + retrieval in parallel" pattern is the canonical RAG win — both are independent network calls, so overlapping them shaves the smaller one off the critical path.

## The traps

- **A blocking call in an async function** stalls the whole event loop — use async clients, or offload sync work to a thread pool.
- **Unbounded concurrency** (gathering 10,000 tasks) exhausts connections — bound it with a semaphore.
- **Error fan-out** — one failed task in `gather` can cancel the rest unless you handle exceptions (`return_exceptions=True`).
</Body>

<Code>
```python
import asyncio

async def answer(query: str, user) -> dict:
    # input guardrail and embedding are independent → overlap them
    safe, qvec = await asyncio.gather(
        check_injection_async(query),
        embed_async(query),
    )
    if not safe:
        return {"refused": True, "reason": "blocked at input guardrail"}

    passages = await retrieve_async(qvec, user)          # depends on qvec
    answer = await generate_async(query, passages)        # depends on passages

    # response is ready; log + output-scan can run concurrently, not on the hot path
    asyncio.create_task(log_interaction_async(user, query, answer))
    return {"answer": answer, "sources": passages}

async def agent_multi_source(query: str) -> list[str]:
    sem = asyncio.Semaphore(8)                            # bound concurrency
    async def guarded(coro):
        async with sem:
            return await coro
    results = await asyncio.gather(
        guarded(search_internal_async(query)),
        guarded(search_web_async(query)),
        return_exceptions=True,                           # one failure doesn't cancel all
    )
    return [r for r in results if not isinstance(r, Exception)]
```
</Code>

<CommonMistakes>
- **Blocking calls in async code** — `time.sleep` or a sync HTTP client freezes the loop
- **Parallelizing dependent stages** — you can't retrieve before you embed
- **Unbounded `gather`** — exhausts connection pools; use a semaphore
- **Ignoring partial failures** — without `return_exceptions`, one error cancels siblings
- **Awaiting fire-and-forget work** — logging/telemetry shouldn't block the response
</CommonMistakes>
