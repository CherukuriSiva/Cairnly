# Deploying cairnly

Three ways to run it, from laptop to cloud:

| Where | How | What runs |
|---|---|---|
| Laptop (Docker) | `docker compose --profile full up -d --build` | db, api, web; Ollama on the host |
| Laptop (Kubernetes) | `scripts/kind-up.sh` | the Helm chart on a local kind cluster |
| AWS | the steps below | ECS Fargate + RDS + ALB, deployed by GitHub Actions |

## AWS architecture

```
internet ─▶ ALB (public subnets) ─┬─ /ask /search /kbs /health ─▶ api (ECS Fargate, 1-4 tasks)
                                  └─ everything else ───────────▶ web (ECS Fargate)
private subnets:  api ─▶ ollama.cairnly.internal (embeddings, CPU)   api ─▶ RDS Postgres 17 + pgvector
                  api ─▶ Claude API (via NAT)                        secrets ─▶ Secrets Manager
```

- Nothing but the load balancer is reachable from the internet.
- The database password is generated by RDS and stored in Secrets Manager; the Claude key is
  put into Secrets Manager by you. Neither is ever in Terraform state, the repo or CI logs.
- A deploy that never becomes healthy rolls itself back (ECS deployment circuit breaker).
- Daily database backups with 7 days of point-in-time restore.

**Rough cost** (us-east-1, idle demo): NAT gateway ~$33, load balancer ~$18, RDS
db.t4g.micro ~$13, Fargate (api + web + ollama) ~$55, logs and secrets ~$3, so about
**$120/month** before Claude usage. `terraform destroy` removes all of it (set
`deletion_protection=false` first).

## First deploy (about 30 minutes)

You need: an AWS account, the AWS CLI logged in as an admin, Terraform 1.6+, and the GitHub
repo already pushed.

1. **Bootstrap once** (state bucket + a GitHub deploy role, no AWS keys in GitHub):

   ```bash
   cd infra/bootstrap
   terraform init
   terraform apply -var github_repo=CherukuriSiva/cairnly    # prints state_bucket and deploy_role_arn
   ```

2. **Tell GitHub** (repo Settings → Secrets and variables → Actions):
   - variables: `AWS_REGION` = `us-east-1`, `TF_STATE_BUCKET` = the `state_bucket` output
   - secret: `AWS_DEPLOY_ROLE_ARN` = the `deploy_role_arn` output
   - create an environment named `production` (optionally require your approval for it)

3. **Deploy:** Actions tab → `deploy` → Run workflow. It pushes images, applies Terraform,
   runs the migrate + ingest job and smoke-tests the URL it prints.

4. **Add the Claude key** (answers need it; until then the API runs but `/ask` errors):

   ```bash
   aws secretsmanager put-secret-value --secret-id cairnly/anthropic-api-key --secret-string "$ANTHROPIC_API_KEY"
   aws ecs update-service --cluster cairnly --service api --force-new-deployment
   ```

5. **HTTPS:** request an ACM certificate for your domain, then run Terraform with
   `-var certificate_arn=<arn>` and point a DNS record at the load balancer.

## Runbook

| Situation | Do this |
|---|---|
| Ship a new version | Run the `deploy` workflow (images are tagged with the commit SHA) |
| Docs changed | Re-run the ingest step: `eval "$(terraform output -raw run_ingest)"`; only changed files are re-embedded |
| `/health` returns 503 | Database unreachable: check RDS status and the `db` security group |
| Answers fail, search works | Claude key missing or wrong: check the secret, then force a new api deployment |
| Search is slow or failing | Check the `ollama` service logs in `/ecs/cairnly/ollama` |
| Roll back | Re-run `deploy` from an older commit, or `terraform apply -var image_tag=<old sha>` |
| Restore the database | RDS console → point-in-time restore → new instance, then update `DB_HOST` via Terraform |
